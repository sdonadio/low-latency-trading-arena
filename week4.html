Custom Allocators, Memory Pools & Runtime Polymorphism

Week 3 taught you to own a lifetime. This week you own the memory itself. malloc is a correct, thread-safe, general-purpose service and it is the single largest source of unbounded jitter in a tick-to-trade path — so you take it out and put a pointer swap in its place. Then you put polymorphic objects in those pools and price the one thing that makes them polymorphic: the virtual call.

  • Explain, with numbers, why the same new call is 22 ns on one tick and 18 µs on the next — and which of those two numbers your deadline actually sees.
  • Build a fixed-size Pool with an intrusive free-list: O(1) allocate, O(1) free, zero fragmentation, and a documented answer for what happens when it runs dry.
  • Choose correctly between a pool, an arena, std::pmr and plain new — including the cases where pooling is the wrong answer.
  • Say why alignas(64) is a latency decision and not a cosmetic one.
  • Explain how virtual works — vptr, vtable, virtual destructor — put a polymorphic object in a pool without leaking, and say what a virtual call costs (Part 4).

Part 1

1What is it? An allocator you sized before the session opened

A custom allocator is not a faster malloc. It is a different contract: you give up generality — arbitrary sizes, unbounded growth, thread safety you did not ask for — and in exchange you get a cost that is the same on every single call. In a system graded on p99.9, a predictable 4 ns beats an average of 22 ns every time.

What the general-purpose heap has to do

malloc serves every size, from every thread, forever. That forces four things into your call: a size-class lookup, a free-list walk that lengthens as the heap fragments, a lock (or a per-thread cache that can miss and then take one), and — when the arena is exhausted — a syscall (mmap/brk) that leaves user space entirely.

None of those four is a bug. Each is the correct implementation of a promise you never needed. The fast path is genuinely fast; it is the distribution that is unusable.

What the hot path needs instead

  • O(1), always. A pointer bump or a free-list pop. No search, no coalescing, no fit.
  • No locks. One pool per thread, so there is nothing to contend for.
  • No syscalls. All memory is reserved before the session opens.
  • No fragmentation. Every slot is the same size, so a freed slot always fits the next request.
  • Bounded. You size it for the worst tick, and you decide what happens past that.

That last one is the part students skip. A pool that silently falls back to new when it is full has all the complexity of a pool and none of the guarantee.

2How does it work? A free-list threaded through the free slots

The fixed-size pool is the cheapest allocator that exists, and it is about twelve lines of real code. One slab, owned once. Every slot is the same size. A free slot has no live object in it, so you store the address of the next free slot inside the slot itself — an intrusive free-list that costs zero extra memory. Allocate is a pop; free is a push.

Size the pool, then abuse it

// include/pool.hpp — HW4. Slot is at least sizeof(void*)
// because a FREE slot stores the next free slot in itself.
template <class T, std::size_t N>
class ObjectPool {
  union Slot { Slot* next; alignas(T) unsigned char buf[sizeof(T)]; };
  Slot  slots_[N];
  Slot* free_ = nullptr;
 public:
  ObjectPool() {                          // thread the list once
    for (std::size_t i = N; i-- > 0;) { slots_[i].next = free_; free_ = &slots_[i]; }
  }
  template <class... A> T* alloc(A&&... a) {
    if (!free_) return nullptr;           // exhausted: caller must cope
    Slot* s = free_; free_ = s->next;     // O(1) pop
    return new (s->buf) T{std::forward<A>(a)...};   // placement new
  }
  void release(T* p) {                    // O(1) push
    if (!p) return;
    p->~T();                              // YOU call the dtor. The pool never does.
    Slot* s = reinterpret_cast<Slot*>(p);
    s->next = free_; free_ = s;
  }
};
Say it out loud. Placement new to construct, explicit ~T() to destroy, pool.release to reclaim. The global allocator is never touched after construction.

Interactive · the arena, and what alignment costs you

A pool needs one fixed size. An arena (bump allocator) does not care about size at all — it keeps one offset, rounds it up to the requested alignment, hands it back, and advances. There is no per-object free; there is only reset(), which reclaims everything in one instruction. Perfect for per-tick scratch. Notice the padding wasted counter as you raise the alignment.

class Arena {
  unsigned char* base_;
  std::size_t    cap_, off_ = 0;
 public:
  Arena(unsigned char* base, std::size_t cap) : base_(base), cap_(cap) {}
  void* alloc(std::size_t n, std::size_t align) {
    std::size_t p = (off_ + align - 1) & ~(align - 1);   // round up
    if (p + n > cap_) return nullptr;
    off_ = p + n;
    return base_ + p;                                    // one add: O(1)
  }
  void reset() { off_ = 0; }              // free EVERYTHING, O(1)
};

Per-thread pools, and the reason they exist

      
A pool with a mutex is a heap with extra steps. The whole point was to remove the
      lock, so give each thread its own pool — feed handler, strategy, order gateway —
      and let objects be produced and consumed on the same thread. When they genuinely must cross a
      thread boundary, hand the object across an SPSC queue and return the
      slot to the pool that owns it, on its own thread. Never free into a pool you do
      not own.

      
Then pad the pools apart. Two per-thread pool objects that land in the same
      64-byte cache line will ping that line between cores on every allocation — false sharing that costs
      you tens of nanoseconds per op for no reason at all. alignas(64) on the pool member
      is the fix, and it is one word.

    

    

      
std::pmr: the standard already did this

      
C++17 factored the idea out. A std::pmr::memory_resource is an abstract
      source of bytes; a std::pmr::polymorphic_allocator lets one container
      type use any resource. So std::pmr::vector<Level> is one type
      whose memory can come from your stack buffer today and a pool tomorrow, with no template churn.

      
    
        
  • monotonic_buffer_resource — a bump allocator over a buffer you supply. release() reclaims all of it at once. This is your per-tick scratch.
    • 
        
  • unsynchronized_pool_resource — pooled fixed-size blocks, no locking. The "unsynchronized" is the feature.
    • 
        
  • synchronized_pool_resource — the same, with a mutex. Not for the hot path.
    • 
        
  • null_memory_resource — throws on allocation. Wire it as the upstream of your monotonic resource and you get a compile-your-mistake-into-a-crash guarantee that you never silently spilled to the heap.

3Why it matters: cache lines, and knowing when not to pool

  
Owning the memory buys you a second thing beyond determinism: you get to decide
  where objects sit. A cache line is 64 bytes on every x86-64 core you will run on,
  and the hardware moves memory in exactly that unit. A struct that straddles a line boundary is not
  slightly slower — it costs an extra line fetch and a split-load penalty on every access, forever.

Cost model, stated. 0.5 cycle of load-port throughput per aligned
      8-byte load (two load ports), +3 cycles for each load that straddles a line boundary, and
      one L1 tag lookup per extra line touched. Measured penalties on recent x86 sit in that range;
      the shape is what matters, not the constant. Clock: 4.0 GHz.

The three real "do not pool" cases

        
    
          
  • It is not on the hot path. A pool you allocate from once at startup buys you nothing and costs a reviewer's afternoon.
    • 
          
  • The size is genuinely arbitrary. A fixed-size pool sized for the worst case wastes most of its slab; an arena or plain new off the hot path is honest.
    • 
          
  • You cannot bound the count. A pool must have an answer for exhaustion. If you have no defensible bound, you do not have a pool — you have a heap with a cliff.

Part 4

  
4Runtime polymorphism — what a virtual call costs

  
Pools give you objects of one type. The moment those objects sit behind a
  common interface — an Order, a Quoter, a Strategy — you are using
  runtime polymorphism: one call site, several bodies, chosen by a hidden pointer in the object.
  It is the right tool for an open set of types and a real cost for a closed one. This part
  builds the mechanism, prices it, and shows how a virtual object lives inside a pool.


  

    

      
Inheritance, and why you hold a Base&

      
Public inheritance is an is-a claim: a Passive can be used wherever a
      Quoter is expected. virtual makes the call late-bound — the
      object decides, not the static type of the reference. override is checked at compile time;
      final forbids further overriding and lets the compiler prove the target.

      
struct Quoter {
  virtual ~Quoter() = default;      // see the rule opposite
  virtual std::int64_t price(std::int64_t mid) const = 0;  // pure
  virtual void on_fill(std::uint32_t) {}  // hook
  std::uint32_t id = 0;
};
struct Passive final : Quoter {
  std::int64_t price(std::int64_t mid) const override { return mid - 1; }
};
struct Aggressive : Quoter {
  std::int64_t price(std::int64_t mid) const override { return mid + 1; }
  void on_fill(std::uint32_t q) override { filled += q; }
  std::uint32_t filled = 0;
};
std::int64_t quote(const Quoter& q, std::int64_t mid) {
  return q.price(mid);   // one call site, any Quoter
}

      
Pass a reference, never a copy.
      Quoter q = passive; would not even compile here (abstract), and with a concrete base it
      slices: only the Quoter part is copied and the call runs the base body.
      Hold Base& or Base*.

    

    

      
The virtual-destructor rule

      
Any class you delete or destroy through a base pointer needs a virtual
      destructor. Without one, only the base destructor runs: everything the derived part owned — a
      std::string buffer, a file descriptor, a lock — is skipped. That is undefined behaviour, and it
      usually looks like it works. Rule of thumb: a class with any virtual function gets a virtual destructor.

      
struct Bad  { ~Bad() {} virtual void f() {} };   // dtor NOT virtual
struct Sub : Bad { std::string tag = std::string(64, 'x'); };
Bad* p = new Sub;
delete p;          // UB: ~Bad only; Sub::tag never destroyed
                       // (clang warns: -Wdelete-non-abstract-non-virtual-dtor)

struct Good { virtual ~Good() = default; };   // the fix

      
An abstract interface is pure virtuals plus a virtual
      destructor and nothing else — no state, no helpers. The same rule applies when you never call
      delete: a pool that calls p->~Base() needs the destructor virtual too
      (third widget below).

Interactive · what one virtual call costs on the hot path

  
The vtable loads are not the bill. The bill is the indirect
  branch when the predictor cannot learn the target, and the inlining you lose because the
  optimiser cannot see through the call. Numbers are the ones measured in class — one laptop, -O2,
  10 M calls — and are order-of-magnitude only: direct/inlined ≈ 0.4 ns,
  virtual with one hot target ≈ 2.2 ns, virtual with four unpredictable targets ≈ 7 ns,
  and final with an exact type is back to direct. Measure yours.

    variant or a template was the right design. Prefer composition to inheritance, keep interfaces
    small, write override everywhere and final often.

struct Order {
  virtual ~Order() = default;      // the switch above
  int id = 0;
};
struct Limit : Order {
  std::string tag = std::string(64, 'x');   // owns a heap buffer
  ~Limit() override { std::puts("~Limit"); }
};
struct Pool {
  alignas(std::max_align_t) unsigned char slab[sizeof(Limit)];
  Order* alloc()          { return new (slab) Limit{}; }  // placement new
  void   release(Order* p) { p->~Order(); }              // virtual: ~Limit, then ~Order
};
int main() { Pool pl; Order* o = pl.alloc(); pl.release(o); }   // prints ~Limit

      
Two rules, one habit. Construct with placement new, destroy with an
      explicit destructor call through a base that has a virtual destructor, then return the slot.
      Never delete a pool pointer. Better still: hand out a unique_ptr with a pool deleter
      so the pair cannot be forgotten. A polymorphic type also costs 8 bytes per object for the vptr —
      budget the pool slot for sizeof(Derived), the largest one.

    

  







  
Part 5

  
5Five ways this goes wrong

  
These are the five that cost marks on HW4, every time. Open them.


  
Falling back to new when the pool is empty
    

      
It looks like defensive programming and it is the opposite. You spent a week removing
      malloc from the hot path, and then you put it back — on exactly the path that runs
      when the market is busiest and the pool is fullest. The fallback fires precisely during the burst
      you built the pool for, so your p99.9 is worse than if you had never pooled at
      all, because now the slow path also carries a branch and a cold cache.

      
Worse, it hides the sizing bug. A pool that silently spills never tells you it was too small,
      so you ship a capacity you never validated.

      
Fix: alloc() returns nullptr, loudly, and the caller
      applies a policy you wrote down — drop the order and count it, reuse the oldest slot, or degrade to
      a cheaper action. Export the exhaustion counter as a metric and treat a non-zero value as a sizing
      defect, not a runtime event.

    


  
Forgetting p->~T() — or calling delete on a pool pointer
    

      
The pool hands you raw bytes; placement new makes them an object. Nothing in that
      chain runs a destructor for you. Skip p->~T() and the slot is still reused
      correctly — so your tests pass — while anything the object owned (a string's
      heap buffer, a file descriptor, a lock) leaks quietly for the rest of the session.

      
The inverse is a crash. delete p on a pointer into your slab tells the global
      allocator to free memory it never owned. That is undefined behaviour and it usually corrupts the
      heap somewhere else entirely, hours later, in a function that is innocent.

      
Fix: exactly one pattern — new (pool.alloc()) T{...} to construct,
      p->~T() then pool.release(p) to reclaim. Better: put that pair inside
      the pool's own release() (as above) or hand out a
      unique_ptr<T, PoolDeleter> so RAII does it and the pattern cannot be forgotten.

    


  
A slot narrower than a pointer, or ignoring alignof(T)
    

      
The intrusive free-list stores a void* inside a free slot. If
      your slot size is sizeof(T) and T is a 4-byte struct, writing the next
      pointer scribbles 4 bytes into the neighbouring slot. The starter's constructor is written
      slot_(obj_size < sizeof(void*) ? sizeof(void*) : obj_size) for exactly this reason.

      
Alignment is the same class of bug with a different symptom. ::operator new gives
      you memory aligned for max_align_t, but your slot stride is yours
      to get wrong: a stride of 40 bytes for a type that needs 16-byte alignment leaves every other slot
      misaligned. On x86 that is a silent slowdown; with SSE/AVX loads or on ARM it is a fault.

      
Fix: slot = max(sizeof(T), sizeof(void*)), then round the stride up to
      alignof(T). Assert it: static_assert(sizeof(Slot) % alignof(T) == 0), and
      declare the storage alignas(T). The union Slot idiom gets both right for free.

    


  
One pool, several threads
    

      
A free-list pop is read head; head = head->next — two operations that are not
      atomic together. Two threads allocating at once hand out the same slot twice,
      and you now have two live objects at one address. This does not crash; it produces one order with
      another order's price, which is the most expensive kind of bug in this course.

      
The reflex fix — wrap it in a std::mutex — reintroduces the unbounded wait you
      removed. The other reflex fix, a lock-free CAS free-list, is a real technique but it also
      reintroduces contention and the ABA problem, and you do not need it yet.

      
Fix: one pool per thread, thread_local or held by the thread's own
      object. Objects are allocated and released on the same thread; when they must cross, pass them
      over an SPSC queue and release the slot on the owning thread. Then alignas(64) the
      pools so two threads' free-list heads do not share a cache line.

    


  
Pooling the wrapper and not the allocation
    

      
ObjectPool<Message, 4096> where Message holds a
      std::string symbol and a std::vector<Level> levels pools
      the outer 48 bytes and nothing else. Every construction still calls
      malloc twice, inside the members you did not look at. Your benchmark shows a lovely
      3.7 ns because it constructs empty objects; your bot shows no improvement at all.

      
The same trap in a different coat: std::pmr::vector<std::string>. The vector's
      buffer comes from your resource; every string in it still goes to the heap, because
      std::string is not pmr-aware. You want
      std::pmr::vector<std::pmr::string>, and the resource has to be propagated.

      
Fix: make hot-path structs flat and trivially destructible — fixed
      char sym[8], std::array<Level, N>, integer prices in ticks.
      Then verify rather than assume: run under a malloc counter (or an upstream
      null_memory_resource) and prove the hot path allocates zero times.
