Data Structures for HFT — The Order Book

The order book is not a container you look things up in. It is a structure you read thousands of times per tick from one hot loop — so its memory layout, not its big-O, decides your p99.9. This week you build the flat, price-indexed mirror that makes the best bid a single load.

  • Name the six operations a book must support — add, cancel, modify, match, best-of-book, queue position — and the cost each one is allowed.
  • Beat std::map with a flat price-indexed array of levels plus intrusive FIFO lists, and say why in cache terms.
  • Size a price band, decide what to do when the market walks out of it, and know when sparsity kills the array.
  • Consume a snapshot-plus-delta feed and refuse to apply a delta after a sequence gap.

Part 1

1What must an order book actually support?

Six operations, wildly different budgets. Five of them happen on the wire's schedule; one of them happens on yours, thousands of times per market-data message — and that is the one to design for.

A central limit order book (CLOB) is resting size at each price, on two sides, ordered by price-time priority: a better price fills first, and within one price the earliest arrival fills first. That second half is the part every naive implementation loses — a level is not a number, it is a FIFO queue, and your position in it is the difference between getting filled and watching the price leave.

The asymmetry that drives every design decision this week: writes are rare, reads are constant. A busy US equity name sends you tens of thousands of book updates a second — a lot, but each one is one write. Your strategy reads the top of book on every one of them, and often several times per message. So you happily pay a little on add and cancel in order to make best_bid() a compare and a multiply.

The starter's contract is deliberately this small — four functions, and the cost of two of them is written into the comment:

// include/order_book.hpp — the HW7 contract. side 'B'=bid, 'S'=ask.
struct Book {
    void   add(uint64_t id, char side, double px, uint32_t qty);
    void   cancel(uint64_t id);
    double best_bid() const;   // O(1)  <- the hot path
    double best_ask() const;   // O(1)  <- the hot path
};
struct SymMap {                // returns (uint64_t)-1 if absent
    void     put(const char* sym, uint64_t id);
    uint64_t get(const char* sym) const;
};
The exchange is the reference. The arena's Python engine (shared/orderbook.py) is a real CLOB: it keys resting orders on (price, seq, id) — a monotonic sequence number, not a timestamp, so ties are impossible — and exposes queue_position(order_id) returning (qty_ahead, level_qty). Your C++ book is a local mirror of that, so on_book can decide without asking anyone.

Part 2

2How does it work? Three layouts, one op stream

Prices are not arbitrary doubles — they live on a fixed tick grid. That single fact turns "look up a price" into "index an array", and takes the whole ordered-container problem off the table.

Here are the three candidates, and the honest version of each. A tree of levels (std::map<int, Level>) is the obvious answer: sorted, handles any price, O(log n). A sorted vector of levels keeps the ordering but makes the storage contiguous, paying a memmove on insert. A flat price-indexed array gives up ordering entirely — index = (px − base) / tick — and gets O(1) everything, at the cost of allocating the whole band up front.

std::map<int, Level>

Red-black tree. One heap node per level, ~48 B of payload plus allocator overhead, all scattered. Finding the touch is begin() / rbegin() — cheap in theory, a chain of pointer hops in practice, and every hop is a fresh cache line.

addO(log n) + one malloc bboO(1) call, O(log n) misseslayoutpointer chasing

sorted std::vector<Level>

Binary search over contiguous memory — the prefetcher cannot help a binary search, but the last three probes land in one line. Insert in the middle shifts everything above it: O(n) bytes of memmove, which is fast per byte and still unbounded.

addO(log n) + O(n) memmove bboO(1), first or last slotlayoutcontiguous

flat array + intrusive FIFO

One std::array<Level, NLEV> per side, indexed by tick. Each level holds aggregate qty plus the head and tail index of an intrusive singly-linked list into one pre-reserved node pool. Cached best_bid_tick makes the touch a scalar read.

addO(1), one indexed store bboO(1), one L1 loadlayoutcontiguous + pooled

Part 3

3Why it is harder than it looks: bands, sparsity, and gaps

The flat array is not free and it is not universal. It buys O(1) with memory, and it assumes the market stays inside the band you allocated. Both assumptions have a bill.

Widget 4 · sizing the price band, and the day the market leaves it

The array must span every price you might see. Widen the band or shrink the tick and the array grows linearly; the occupied levels do not. Push the reference price past the edge and you pay a rebase.

// The whole policy, and it is four comparisons. Refusing to guess is the feature.
struct Feed {
    uint64_t expected = 0;          // next seq we are entitled to apply
    bool     stale    = true;       // true until a snapshot lands
    uint64_t gaps     = 0;

    void on_snapshot(uint64_t seq) { expected = seq + 1; stale = false; }

    bool on_delta(uint64_t seq) {
        if (stale)           return false;         // waiting for a snapshot
        if (seq <  expected) return false;         // duplicate: drop, do not re-apply
        if (seq >  expected) { ++gaps; stale = true;  // GAP: our book is now a guess
                               return false; }        // re-request instead
        ++expected; return true;                     // in order: apply it
    }
};

The whole book, as you will write it

Flat price-indexed levels, an intrusive FIFO per level over one pre-reserved node pool, cached touch indices, and queue_ahead that walks only your own level. This compiles under clang++ -std=c++20 -O2 -Wall -Wextra.

constexpr double TICK = 0.01;
constexpr int    NLEV = 1 << 16;              // 65 536 ticks = $655.36, contiguous
constexpr uint32_t NIL = ~0u;

struct Level { uint32_t qty = 0, head = NIL, tail = NIL; };  // aggregate + FIFO ends
struct Node  { uint32_t qty, next; int tick; char side; };   // intrusive, pooled

struct Book {
    std::array<Level, NLEV> bid{}, ask{};
    std::vector<Node> pool;                   // reserve()d once; index = order slot
    int best_bid_tick = -1, best_ask_tick = NLEV;

    static int to_tick(double px) { return int(px / TICK + 0.5); }

    uint32_t add(char side, double px, uint32_t qty) {
        int t = to_tick(px);
        Level& L = (side == 'B') ? bid[t] : ask[t];
        uint32_t slot = uint32_t(pool.size());
        pool.push_back({qty, NIL, t, side});            // no allocation: reserved
        if (L.tail == NIL) L.head = slot; else pool[L.tail].next = slot;
        L.tail = slot;                                  // price-time: append at the back
        L.qty += qty;
        if (side == 'B') { if (t > best_bid_tick) best_bid_tick = t; }
        else             { if (t < best_ask_tick) best_ask_tick = t; }
        return slot;
    }
    // O(1) reads — the hot path never scans
    double best_bid() const { return best_bid_tick < 0     ? 0.0 : best_bid_tick * TICK; }
    double best_ask() const { return best_ask_tick >= NLEV ? 0.0 : best_ask_tick * TICK; }

    // qty resting in front of `slot` at its own level: your fill probability
    uint32_t queue_ahead(uint32_t slot) const {
        const Node& me = pool[slot];
        const Level& L = (me.side == 'B') ? bid[me.tick] : ask[me.tick];
        uint32_t ahead = 0;
        for (uint32_t i = L.head; i != NIL && i != slot; i = pool[i].next)
            ahead += pool[i].qty;                       // walks only your level
        return ahead;
    }
};
Read the add path again. One indexed store into bid[t], one push_back into a reserved pool, two integer compares. No allocation, no tree rotation, no memmove — and the touch update is a single comparison because a new order at or inside the touch can only ever improve it.
Part 4

4Five ways a fast book turns out to be wrong or slow

Every one of these passes a unit test. Open them.

Computing the BBO by scanning, on the read path

best_bid() loops down from the top of the array looking for the first non-empty level. With the touch at tick 9 990 out of 65 536 that is ten thousand iterations, most of them over cold memory, and you call it four times per message.

The fix is not a faster loop, it is not looping. Maintain best_bid_tick as a cached scalar and pay for it on the write path, where you have message-rate budget instead of per-read budget. The asymmetry — rare writes, constant reads — is the whole reason this trade is free.

Fix: cache the touch index. add only ever improves it (one compare); cancel is the only operation allowed to scan, and only when it empties the inside level.

Forgetting to advance the touch when a cancel empties the inside level

cancel subtracts the qty and returns. The level is now zero but best_ask_tick still points at it, so best_ask() keeps returning a price where nothing rests. Your bot crosses a spread that is not there, and the tests never catch it because they cancel away from the touch.

The mirror image is worse: a side that empties completely leaves the index pointing into the array instead of at the sentinel, and best_ask() reads a stale tick forever.

Fix: after any cancel at the touch, walk one tick at a time until you find size — it is a contiguous scan and the common case runs zero iterations. If you run off the end, reset to the sentinel and make best_ask() return 0.0. Test the empty-side case explicitly.

std::unordered_map<std::string, Order> on the hot path

It looks like O(1). Per lookup you hash a std::string (a pointer chase to the heap unless it is short enough for SSO), then follow a bucket pointer to a node allocated somewhere else entirely — two or three likely misses, so 100–200 ns for an "O(1)" operation. Insert can rehash, which is an unbounded pause on a random message.

Both halves of the problem are layout, not asymptotics: chaining scatters your data, and std::string keys turn a key comparison into a dereference.

Fix: open addressing over a flat power-of-two table, fixed-size inline char[16] keys, mask instead of modulo, and reserved once at start-up so it never rehashes. That is exactly what SymMap in the starter asks for, and it is one contiguous probe.

Indexing the array with a rounded double

int t = int(px / TICK); — and 101.99 / 0.01 evaluates to 10198.999999999998, so the truncation puts the order one tick low. Half your book is now shifted by a cent and your spread reads as negative on a name whose price happens to land on the wrong side of a binary fraction.

Rounding with + 0.5 covers this case, but the real fix is to stop carrying prices as doubles at all: the exchange sends you an integer number of ticks, the tick grid is fixed, and every arithmetic step you do in floating point is a chance to lose a cent.

Fix: parse prices to integer ticks at the edge of the system and keep them integral all the way through the book. Convert back to a double once, at the boundary where a human or a log needs it. Assert t is inside the band before you use it as an index.

Applying a delta after a sequence gap

Seq 104 arrives when you expected 103. You apply it, because the alternative is having no book. From that moment your local book and the exchange's disagree, silently and permanently — you never see an error, you just quote a level that emptied thirty seconds ago and get adversely selected on every fill.

This is the one failure on this page that costs money rather than microseconds, and it is the reason the sequence number exists. A book that is fast and wrong is worse than one that is slow and honest, because you will size positions against it.

Fix: on a gap, mark the book stale, stop quoting, and re-request a snapshot. Widget 5 is the ledger for each policy — read the "book wrong by" number for apply it anyway and compare it to the "time stale" cost of doing it properly.
