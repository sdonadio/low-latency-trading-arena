Memory Management & Smart Pointers

There is no garbage collector coming to help you, and that is the point: in C++ you decide who owns each object and exactly when it dies. Get that right and cleanup is free, deterministic and invisible in your latency histogram. Get it wrong and you have a leak that grows all session, or a pointer into memory somebody else now owns.

  • Use RAII as an ownership contract: acquire in the constructor, release in the destructor, and let the compiler run it on every exit path — including the one an exception takes.
  • Choose deliberately between a raw non-owning pointer, unique_ptr, shared_ptr and weak_ptr, and price the choice in nanoseconds.
  • Read a move as “steal three pointers”, not “copy quickly”, and know which functions give you one for free.
  • Lay out a struct so that the fields on_book reads share a cache line — and so that two threads' counters do not.

Part 1

1What is it? A destructor you cannot forget to call

RAII is one sentence: acquire the resource in the constructor, release it in the destructor. What makes it powerful is not tidiness — it is that the compiler emits the destructor call on every path out of the scope, including the path an exception takes while unwinding the stack. Step through the same function twice, once with a raw new and once with unique_ptr, and throw the risk veto.

unique_ptr is not a compromise. It is exactly the size of a
      raw pointer, its operator* compiles to the same load, and with the default deleter
      there is nothing extra stored at all. The only thing you give up is the ability to
      copy it — which was never a feature, since two owners of one object is the bug
      the type exists to prevent.

      
#include <memory>

struct Level { double px; int qty; };

// unique_ptr is a pointer, with a destructor attached
static_assert(sizeof(std::unique_ptr<Level>) == sizeof(Level*));

// shared_ptr is two pointers: the object and the control block
static_assert(sizeof(std::shared_ptr<Level>) == 2 * sizeof(Level*));

    

  


  
make_shared, new, and custom deleters

  

    

      
// Two allocations: one for the Level, one for the
// control block — and they land far apart in memory,
// so touching the refcount misses the cache.
std::shared_ptr<Level> a(new Level{100.02, 500});

// One allocation: object and control block fused into
// a single block, adjacent in memory. Also
// exception-safe, which the line above is not.
auto b = std::make_shared<Level>(100.02, 500);

// unique_ptr's equivalent, for the same reasons
auto c = std::make_unique<Level>(100.02, 500);

      
Prefer the factory. The one case where make_shared loses: it keeps the
      whole fused block alive as long as any weak_ptr exists, so a huge object watched by a
      long-lived weak_ptr is better built with new.

    

    

      
// A custom deleter turns unique_ptr into RAII for
// anything with a paired acquire/release — not just
// memory. This is the pattern for every C API you
// will meet in weeks 11–13.
#include <cstdio>
#include <memory>

struct FileCloser {
    void operator()(std::FILE* f) const noexcept {
        if (f) std::fclose(f);
    }
};
using FilePtr = std::unique_ptr<std::FILE, FileCloser>;

FilePtr open_tape(const char* path) {
    return FilePtr{std::fopen(path, "rb")};   // closed on every path out
}

// A stateless deleter costs nothing: still one pointer.
static_assert(sizeof(FilePtr) == sizeof(std::FILE*));

      
A stateless deleter is stored in no bytes at all thanks to empty
      base optimisation. A capturing lambda or a std::function deleter is not — it doubles
      the pointer's size and can cost you an indirect call.

And the same 64 bytes, from the other direction.
  Padding you did not want costs you cache lines; padding you did want buys you
  isolation. Two counters written by two different threads must not share a line, or every write
  invalidates the other core's copy — alignas(64) on each is the fix, and it is why
  sizeof going up is sometimes the optimisation. Week 9 explains the
  coherency traffic; Week 10 depends on the fix.







  
Part 4

  
4Five ways this goes wrong

  
Every one of these has shipped in a submission. Open them.


  
An early return, or a throw, between new and delete
    

      
The code is correct on the happy path and leaks on every other one. A risk check that returns
      early, a break added six months later, an exception from a constructor two frames
      down — each of them skips your delete, and in a process that runs all session the leak
      is unbounded.

      
It survives review because the delete is visibly right there, a
      few lines below the new.

      
Fix: never own through a raw pointer. std::make_unique puts the
      delete in a destructor, and the compiler emits that destructor on every exit path
      whether you thought of it or not.

    


  
shared_ptr everywhere, because it always compiles
    

      
shared_ptr is the path of least resistance: it copies, so nothing ever fights you.
      What you have bought is a second allocation, sixteen bytes per handle, an
      atomic increment on every copy and an atomic decrement on every destruction —
      and a control block that lives somewhere else in memory, so touching the refcount is frequently a
      cache miss on top.

      
Worse, it makes the ownership question unanswerable. When everything is shared, nothing has a
      lifetime you can reason about, and “when is this object destroyed?” becomes a runtime mystery.

      
Fix: unique_ptr for ownership, raw references for observation, and
      shared_ptr only when two owners genuinely both extend the lifetime. On the
      tick-to-trade path, none.

    


  
A pointer or reference into a container that can reallocate
    

      
std::vector::push_back may move the entire buffer, which invalidates every pointer,
      reference and iterator into it. Caching &book.bids().front() across an insertion is
      a use-after-free that reads the right value until the allocator reuses the bytes.

      
The same trap with std::string, and with a std::string_view that
      outlives the string it viewed.

      
Fix: store an index, not an address, when the container can grow.
      If you need stable addresses, reserve() the maximum up front — which you should be
      doing anyway, since Week 2 said no allocation on the hot path — or use a container with stable
      references such as std::deque, or Week 4's pool.

    


  
A shared_ptr cycle, and a leak with no new in sight
    

      
Two objects holding shared_ptrs to each other keep each other's strong count at one
      forever. Neither destructor ever runs, and no tool that looks for missing deletes will
      say a word — the refcounts are perfectly consistent, just never zero.

      
This appears the moment your order objects point back at the book, or a subscriber list holds the
      subscribers that hold the list.

      
Fix: exactly one direction of a cycle owns. The other holds a
      weak_ptr and calls lock() when it needs access — which also, usefully,
      forces you to handle the case where the object is already gone.

    


  
Reading a moved-from object
    

      
After std::move(o), o is valid but
      unspecified. For a std::vector that means empty in practice; for a user-defined
      type it means whatever that type's move constructor chose to leave behind, which the standard does
      not tell you. Code that reads o.size() afterwards is relying on a coincidence.

      
The subtle version: f(std::move(x), g(x)) — the argument evaluation order is
      unspecified, so g may see x before or after it was plundered.

      
Fix: after moving from an object, only destroy it or assign a fresh value to it.
      Never move the same object twice, and never move from something you use later in the same
      expression.
