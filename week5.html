Templates & Generic Programming

You wrote one pool by hand last week. Write it once instead, and let the compiler stamp out a version for every type you need. A template is not a runtime abstraction that happens to be fast — it is code generation, finished before main starts, and the machine code it emits is the code you would have written by hand.

  • State the actual cost of a virtual call — vtable load, indirect branch, and the inlining barrier — and say which of the three dominates.
  • Write function and class templates, and predict exactly which instantiations your code generates and what they cost in bytes.
  • Constrain a template with a C++20 concept instead of an enable_if, and read the error message it produces.
  • Branch at compile time with if constexpr so the dead arm is never instantiated — and know when a plain if would not have compiled at all.
  • Defend the trade-off you just made: binary size, instruction cache and build time.

Part 1

1What is it? Polymorphism that finishes before the program starts

There are two ways to write one algorithm that works for many types. A virtual function decides which code to run while the program is running, from a pointer it has to load. A template decides while the program is being compiled, and then there is nothing left to decide. Both are polymorphism. Only one of them is free.

What a virtual call actually costs

  • The vtable load. Read the hidden pointer at the front of the object, then read the slot. Two dependent loads before you know where you are going.
  • The indirect branch. The CPU guesses the target from the branch-target buffer. One concrete type in the mix: it guesses right. Several: it does not.
  • The inlining barrier. This is the expensive one. The compiler cannot see through the call, so no inlining, no constant folding, no cross-call scheduling, and arguments go through the ABI instead of staying in registers.
Read that order again. Students quote the vtable load; the real bill is the optimisations the compiler was not allowed to perform.

What a template does instead

A template is a recipe, not code. Nothing is emitted until you use it with a concrete type; at that point the compiler instantiates it — generates one real function or class for that type — and from then on the call is an ordinary direct call to an ordinary function whose body it can see, inline and fold.

The price is that the type set has to be known at compile time, and every distinct instantiation is separate machine code. That is the whole trade, and Part 3 makes you put a number on it.

Stroustrup's promise. “You don't pay for what you don't use, and what you do use, you couldn't hand-code better.” Templates are how the second half is delivered.

The workload

Cost model, stated. The work itself is 1.20 ns. Virtual adds 0.90 ns (two dependent loads for the vtable slot), 0.80 ns (indirect call and return), 1.10 ns (arguments through the ABI, no constant folding), plus a 15-cycle mispredict at 4.0 GHz on the fraction of calls the BTB gets wrong. Inlining lets the template constant-fold sizeof and drop to 0.75 ns. Directional, not a benchmark — measure your own.
// runtime polymorphism: one vtable, one indirect call
struct ICodec {
  virtual std::size_t enc(Buf&, std::int64_t) const = 0;
  virtual ~ICodec() = default;
};
std::size_t hot_virtual(const ICodec& c, Buf& b, std::int64_t v) {
  return c.enc(b, v);                 // load vtable, load slot, jump
}

// compile-time polymorphism: no base class, no vtable
struct FastTickCodec {
  std::size_t enc(Buf& b, std::int64_t v) const {
    std::memcpy(b.p, &v, sizeof v); return sizeof v;
  }
};
template <class C>
std::size_t hot_template(const C& c, Buf& b, std::int64_t v) {
  return c.enc(b, v);                 // direct, inlined, folded
}

Part 2

  
2How does it work? Deduce, constrain, branch — all at compile time

  
Three mechanisms carry almost every generic thing you will write this term.
  Deduction means you rarely spell out the type. Concepts say which
  types are allowed, in one word, with an error message a human can read. if
  constexpr lets one function body contain several mutually incompatible
  implementations, because the compiler throws away the ones it did not pick.


  

    

      
Deduction & specialization

      
max_of(3, 4) deduces T = int; you never write
      <int>. When one type deserves bespoke treatment you specialise:
      a full specialization for exactly that type, or a partial one for a family
      (Ptr<T*>). Overload the hot type when the generic body is a cycle too slow —
      but measure first.

    

    

      
Traits: asking about a type

      
std::is_integral_v<T>,
      std::is_trivially_copyable_v<T>, std::is_same_v<A,B> resolve
      to true/false before the program runs.
      std::remove_reference_t, std::decay_t,
      std::conditional_t compute new types. Write your own: a trait is
      just a template with a static constexpr bool value.

    

    

      
Packs and folds

      
template <class... Ts> binds a whole list;
      sizeof...(Ts) is its length at compile time. A C++17 fold collapses the pack over an
      operator in one line — (xs + ...), or (encode(b, fs), ...) to write a
      whole message. No recursion, no base case, and it unrolls completely.

Three ways to keep the generality and lose the bloat

      
    
        
  • Hoist the non-dependent part. Anything in the body that does not mention T belongs in an ordinary non-template function the instantiations call. One copy instead of twenty.
    • 
        
  • Normalise the type before you instantiate. std::string, const char* and char[8] are three different Ts and three copies of the same algorithm. Take a std::string_view and you have one.
    • 
        
  • Type-erase the cold path only. Configuration, reporting and the shutdown sequence can be virtual. Keeping the hot path monomorphic is the point; making everything a template is not.
    •

Part 4

  
4Five ways this goes wrong

  
These are the five that cost marks on HW5, every time. Open them.


  
Putting the template's body in a .cpp
    

      
You declare template <class T> std::size_t put(Buf&, const T&); in the
      header and define it in codec.cpp. It compiles. Then the link fails with
      undefined reference to put<long>(...) and the message looks
      like a build-system problem, which it is not.

      
A template is not code — the compiler can only emit put<long> at the point
      where it can see both the use and the definition. Your translation unit saw the
      declaration, so it emitted a call; the one that had the definition never saw a use, so it emitted
      nothing.

      
Fix: define templates in the header (that is why the STL is header-only), or, if you
      genuinely want to hide the body and you know the complete type set, use
      explicit instantiation: template std::size_t
      put<std::int64_t>(Buf&, const std::int64_t&); in the .cpp, one line
      per type. That also caps the bloat — at the cost of the type set no longer being open.

    


  
Using a plain if where you needed if constexpr
    

      
if (std::is_integral_v<T>) memcpy(out, &v, sizeof v); else return
      encode(v.data(), v.size()); reads fine and fails to build for T = int, because
      both arms of a runtime if must compile for every instantiation —
      and int has no .data(). The condition being a compile-time constant does
      not save you; it is still an if.

      
The same mistake in reverse is subtler: with if constexpr the discarded arm is not
      instantiated, so a genuine bug living in a branch no type ever selects will sit there silently for
      the rest of the term until someone adds the type that reaches it.

      
Fix: if constexpr whenever the condition is a property of
      T. Terminate the chain with else static_assert(always_false<T>,
      "unhandled type") — a dependent-false helper, because a bare
      static_assert(false) fires even in a discarded arm — so a type you forgot is a
      readable build error instead of a silent fall-through.

    


  
T&& is not always an rvalue reference
    

      
In template <class T> void submit(T&& o), T&& is a
      forwarding reference: it binds to lvalues and rvalues alike, and T
      is deduced as Order& in the first case. So std::move(o) inside that
      function will happily gut a caller's live object — you moved from something the caller still owns
      and still uses.

      
The tell is that it works in every test, because your tests pass temporaries. It breaks the
      first time the call site passes a named variable, which is the first time it matters.

      
Fix: in a pass-through, always std::forward<T>(o), never
      std::move. std::move is for when you own the object and are done with
      it. And remember the asymmetry: in template <class T> class Pool { void
      push(T&&); }, T is already fixed by the class, so that
      T&& really is an rvalue reference.

    


  
Instantiating the same algorithm three times by accident
    

      
send("AAPL"), send(sym_string) and send(sym_view) look
      like one function used three ways. They are send<char[5]>,
      send<std::string> and send<std::string_view> — three
      complete copies of your serialiser in .text, doing identical work. Multiply by the
      number of call sites and templates and you can add tens of kilobytes to a hot path that has
      32 KB of L1i to live in.

      
The cost does not show up as a slower call. It shows up as instruction-fetch misses at the
      start of a tick, which is a p99 problem with no line of code to blame.

      
Fix: normalise at the boundary — take std::string_view and
      std::span<const std::byte> so there is one T. Hoist every line that
      does not mention T into a non-template helper. Then check: nm -C --size-sort
      your_bot | tail -40 lists your largest symbols, and duplicated instantiations are obvious
      in that list.

    


  
Forgetting typename, and shipping the error wall
    

      
typename Container::value_type x; needs the typename keyword because
      at definition time the compiler cannot know whether Container::value_type names a
      type or a member — the name is dependent on T, and the default
      assumption is “not a type”. The sibling case is obj.template get<0>(), where
      without template the < parses as less-than.

      
The larger version of this pitfall is what you hand to whoever reads your error: an unconstrained
      template that a wrong type reaches will fail deep inside your codec and print the whole
      instantiation stack. The bug is one line at the call site; the message is two screens from
      somewhere else.

      
Fix: typename for dependent types, .template for dependent
      member templates. Then constrain the entry point — template <Encodable T>, or
      void send(Encodable auto& m) — so a wrong type fails at
      your constraint with your name on it. That is the real reason concepts beat
      enable_if: not brevity, error quality.
